# ポジショニングと対外コミュニケーション

[English](./positioning.md)

Wasabi Table の製品定義、差別化の語り方、競合に関する記述ルールをまとめたドキュメントです。README・デモ・リリースノート・SNS など対外向け文案の判断基準として使います。

## 製品定義（1文）

**Canvas + Rust/WASM による、Excel 風操作の高性能データグリッド。npm 数行で始められ、列定義・大規模 records・フィルター/テーマまで段階的に深掘りできる。**

## カテゴリ上の位置づけ

Wasabi Table は次のカテゴリに属します。

| カテゴリ | 説明 | Wasabi の関係 |
|----------|------|---------------|
| DOM / 仮想スクロール型グリッド | リッチ UI・大量機能・エンタープライズ向け | **用途が異なる**（DOM コスト・ bundle サイズ） |
| Headless テーブル | UI をすべてアプリ側で構築 | **操作感を最初から提供**（Excel 風 UX） |
| Canvas データグリッド | 大規模リスト・高速スクロール | **主戦場** |
| フルスプレッドシート | 数式・ピボット・チャート連携 | **対象外**（意図的にやらない） |

## 差別化の訴求軸（名指しなし）

対外文案では、競合名ではなく次の軸で語る。

1. **予測可能な性能** — セル単位 DOM を作らない Canvas 描画。描画・ヒットテスト・viewport 計算を Rust/WASM 側で完結。
2. **大規模データ** — `dataSource.records` と viewport 同期により、論理行数とメモリ使用量を分離。
3. **段階的な API** — Tier 1（3行で表示）→ Tier 2（列定義・リスナー）→ Tier 3（records・フィルター・テーマ・上級 API）。
4. **データ整合性** — 列型・バリデーションを WASM コアに置き、アプリ側は列定義を渡す。
5. **計測の透明性** — 自社ベンチマークページで再現可能な数値を公開する。

## ユーザー動線（Progressive Disclosure）

公式ドキュメントの章立て・デモ構成は次の 3 Tier に揃える。

### Tier 1 — 30秒（デフォルト体験）

```typescript
const table = await WasabiTable.create(canvas);
table.setCellValue(0, 0, 'Hello');
table.render();
```

**伝えること**: 軽い・速い・追加 UI 不要で Excel 風操作が使える。

### Tier 2 — アプリ組み込み

- `createWasabiTableWithListeners`（セル参照・入力バー・統計）
- `setColumnHeaders` + フィールド型（バリデーション）
- `applyTheme` / イベントハンドラ

**伝えること**: 業務画面の一覧・編集 UI がここで完成する。

### Tier 3 — 大規模・カスタム

- `dataSource.records`（viewport 同期）
- フィルター/ソート、条件付き書式、カスタムテーマ
- `filter-sort.ts` の単体利用、`RecordsDataSource` 連携

**伝えること**: 大規模マスタ・ログビュー向け。必要ならモジュール単位で踏み込める。

## 1.0 スコープ外（明示する）

README や Getting Started 末尾で、**やらないこと**も併記する。

- 数式エンジン（`=SUM` 等）— 数式バーはセル値エディタであり、表計算機能ではない
- ピボット・チャート・ピボット連携
- セル結合
- フレームワーク専用コア（React 等へのロックイン）
- サーバーサイドレンダリング（WASM + Canvas はブラウザ専用）
- リアルタイム共同編集

## 競合・比較に関する記述ルール

### 原則

| ルール | 理由 |
|--------|------|
| README 等の表向き文案で**競合製品名を並べた比較表を置かない** | 更新コスト・偏り・論争・期待値ミスマッチを避ける |
| **カテゴリ比較**（DOM 型 / Headless / Canvas / スプレッドシート）で位置づける | 差別化は維持しつつ摩擦を抑える |
| 性能は**自社ベンチの数値 + 再現手順**で示す | 「〇〇より速い」より安全で信頼される |
| 「〇〇代替」「〇〇キラー」は使わない | 機能スコープのすり替えとクレームを招く |
| 競合ロゴ・UI スクショを無断で比較素材に使わない | 商標・著作権リスク |

### 許容する表現

- 「Canvas ベースのデータグリッドとして、大規模 records の表示・編集に特化している」
- 「benchmark ページで同条件の計測結果を公開している（[Benchmark](../examples/npm-package/benchmark.html)）」
- 「数式エンジンやピボットが必要な場合は、フルスプレッドシート系製品の検討が適切」

### 控えめな名指し（任意・docs 内のみ）

選定ガイド（将来の `docs/choosing-a-grid.ja.md` 等）に限り、**中立な位置づけ**として記載してよい。

- 良い例: 「CheetahGrid の records API に近い思想を持つ（互換 API ではない）」
- 悪い例: 「CheetahGrid より速くて軽い」

Issue・Discussion で個別に聞かれた場合は、事実ベースで回答してよい。ただし README に昇格させない。

### ベンチマーク

- 公開するのは **Wasabi Table 単体の計測結果**と環境・手順
- 同等データ形状（例: `CHEETAH_STYLE_COLUMNS`）での計測は可。第三者製品名を結果表に並べない
- 数値に再現 URL（`benchmark.html`）を必ず添える

## 内部用（非公開メモ）

競合機能表・勝敗分析・価格比較などは **リポジトリにコミットしない**（Notion / ローカルメモ推奨）。公開 docs と混在させない。
